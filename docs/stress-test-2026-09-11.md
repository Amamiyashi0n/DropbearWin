# Windows 压力测试记录：2026-09-11

结论：当前 x64 和 x86 交付程序通过本次有界压力测试，测试负载下未发现命令失败、
文件内容错误、监听进程崩溃或测试结束后的已观察进程残留。24 个已认证连接是
本次测试的最高梯度，不代表容量上限。本次没有修改服务端实现。

## 环境与负载

本机 Windows，Python 报告版本 `Windows-10-10.0.19044-SP0`，8 个逻辑处理器。
通过 MSYS2 CLANG64 调用原生 Windows Python，使用 Paramiko 和 psutil。
客户端与服务端运行在同一台机器，只绑定 127.0.0.1，两个架构顺序运行。
每轮使用一次性账号、数据目录、随机端口；结束后回收测试服务进程和数据。

每个架构的主负载：

- 4、12、24 个已认证连接，每连接连续执行 10 条命令，共 400 条。
- 每个梯度每连接打开 2 次交互式 Shell，共 80 次，校验欢迎页和资源字段。
- 24 路同时上传并下载 1 MiB 文件，逐字节校验，共 48 MiB 双向有效载荷。
- 4 路并发，完成 100 次登录、执行命令、断连；主负载命令总计 500 条。
- 额外验证认证前每 IP 5 个、总计 30 个连接的限制，以及断连/认证成功后释放名额。
- 负载结束后检查子进程归零、监听进程仍可执行命令，停止后检查观察到的进程存活情况。

已认证负载阶段串行完成认证，避免将正常的认证前限流误计为执行故障。

资源每 250 ms 采样；工作集是服务端监听、连接及命令进程工作集之和，可能重复
计算共享页，不含测试客户端，也不代表机器新增物理内存。短于采样周期的进程可能
未被观察。两个架构监听句柄均增加 1，本轮没有长期趋势数据，据此不作“绝无泄漏”结论。

## 性能观察与边界

24 个连接各连续执行 10 条简单 echo 命令时，批次 P95 为 x64 13.48 秒、x86
12.79 秒。这里是每连接 10 条命令的总耗时，不是单条命令 P95。短命令响应仍有
优化空间：Windows 会话循环通过最长 1 秒的超时轮询子进程退出，可能贡献这一
延迟；需要单独分段计时才能确认各环节占比，本次没有直接改动该机制。

本轮为约两分钟/架构的短时压力测试，不是数小时/数天的稳定性测试；没有覆盖
外部网络、网络抖动、XP/Server 2003 实机或最大连接容量。主压力负载使用默认 CMD，
PowerShell 和 SCM 生命周期属于已有独立回归测试范围。

## 复现与原始记录

脚本：`tests/windows_stress.py`。构建机需要 Paramiko、psutil，部署机不需要。

```text
python tests/windows_stress.py dist/dropbear-win-x64.exe build/stress-x64.json
python tests/windows_stress.py dist/dropbear-win-x86.exe build/stress-x86.json
```

本地原始记录为 `build/stress-x64.json`、`build/stress-x86.json` 及同名 `.log`。
JSON 包含测试二进制 SHA-256、各批次成功数/延迟、资源统计和错误列表；`build/`
为 Git 忽略的生成目录，后续重跑会覆盖同名记录。
