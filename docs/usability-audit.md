# Windows 使用性排查与验证（2026-09-11）

这次排查从实际启动、连接、退出和部署流程出发。先前的命令与吞吐压测没有覆盖
重复启动和控制台可读性，遗漏了 Windows `SO_REUSEADDR` 导致的重复绑定问题。
修复后的行为和对应验证列在下表；以实际运行结果为准，不把“能够编译”当作功能验证。

## 修复与回归范围

| 使用场景 | 当前行为 | 回归证据 |
| --- | --- | --- |
| 首次启动 | 完成账号设置后可立即认证执行命令 | `windows_usability.py` 首次配置 |
| 非默认端口重复启动 | 新实例非零退出，旧实例仍可执行命令 | 同端口两个进程、核对唯一监听 PID |
| 22 连续重开 | 终止旧监听及任务树，再独占绑定 | 连续 3 次接管，旧任务 PID 消失，新连接可执行 |
| 同时启动多个实例 | 启动接管串行化，最终只有一个监听实例 | 3 个竞争启动进程，核对存活及监听 PID |
| 旧版实例无退出监视器 | 按实际监听 PID 的进程树回收 | 独立 TCP 监听程序及其无监视器子进程 |
| 旧账号和主机身份 | 接管不重建账号/主机密钥 | 连续接管前后文件字节保持一致 |
| 权限不足 | 报监听 PID 和 Windows 错误，新实例失败，旧实例保留 | 对测试进程设置拒绝终止 DACL；仅禁用新测试进程特权后验证 |
| IPv6 22 | 同样查询占用者并独占接管 | `::1` 旧/新监听 PID 核对 |
| SSH 转发到占用端口 | 请求失败，不触发进程接管或部分地址成功 | 请求转发 22 后原 SSH 会话仍可执行 |
| 多个监听地址/端口部分失败 | 整体启动失败，不显示 RUNNING | 一空闲端口加一冲突端口 |
| Ctrl+C / Ctrl+Break / 关闭窗口 | 清理任务与 PID 文件，释放监听 | 实际控制台事件、WM_CLOSE 和立即重启 |
| 残留 PID 文件 | 不信任旧 PID；成功启动后记录实际 PID | 写入过期 PID，再启动验证 |

| 帮助、版本 | 无账号时也立即显示，不进入首次配置 | `-h` / `-V` 加空账号目录 |
| 坏账号配置、错误 Shell | 明确报错，非零退出，不误报 RUNNING | 空配置、错误哈希结构、错误 Shell 名称 |
| 带空格/中文的 EXE 路径 | 能启动连接子进程并执行命令 | 将 EXE 复制至带空格和中文的临时目录 |
| 服务和控制台互相接管 | 旧服务/控制台进程结束，新实例可认证 | 真实 SCM 注册、运行、双向接管、停止和删除 |
| 部署产物识别 | 两个架构 EXE 和生成的 SHA-256 清单 | `dist/build-manifest.json` 与实际文件核对 |

服务端改动保留输出排空与进程退出通知机制。原有 `windows_native.py`、
`windows_lifecycle.py --service`、`windows_stress.py` 和短命令延迟测试用于检查这次
修改是否影响 CMD/PowerShell、二进制输出、SFTP、服务启停、认证限流及响应速度。

最终交付文件验证结果：两个架构各 14 组使用性测试通过；原生命令/传输 4 组、
生命周期 10 组通过；两个架构各重新完成 500 条命令、80 次欢迎页、24 路文件往返
的压力测试，均无错误，静置后子进程归零。压力记录的二进制 SHA-256 已与产物清单
逐项核对。最后单独测得短命令中位延迟：x64 有输出/无输出约 77/78 ms，x86
约 76/73 ms。短命令测试各预热 5 次、统计 30 次，完整记录见
`build/latency-usability-x64.json`、`build/latency-usability-x86.json`。

## 实现要点

Windows 监听改用 `SO_EXCLUSIVEADDRUSE`，设置失败不会降级成共享监听。启动层
仅对 22 启用接管，SSH 连接子进程及转发请求不启用。接管查询 IPv4/IPv6 TCP
监听表，打开实际进程句柄，回收旧进程树并等待退出，再尝试独占绑定。进程树检查
使用进程创建时间排除比父进程更早的记录，避免把过期父 PID 当作关系依据。

窗口关闭处理等待监听线程清理后再返回，避免 Windows 在 handler 返回时立即终止
程序，跳过 PID 文件与子进程清理。控制台启动时显式取消从启动器继承的“忽略 Ctrl+C”
属性；真实 Ctrl+C 回归曾复现原先不退出的行为，修复后两个架构均验证清理成功。
日志互斥量由监听进程创建并传给连接进程；普通日志先格式化再整行写出，exec
字节调试记录也使用同一把锁，覆盖完整输出过程。失败启动不会覆盖旧实例的 PID 文件。

`dist/` 不再保留旧版 EXE。构建产物清单记录本次构建实际产生的文件；既有账号和
密钥目录没有删除。

## 运行与证据位置

在 MSYS2 CLANG64 入口调用原生 Windows Python；测试机安装 Paramiko 和 psutil。
完整服务测试需要管理员权限。22 测试先确认本机该端口无监听，只接管自己
创建的一次性程序；所有测试服务使用随机名称并在结束后删除。

```text
python tests/windows_usability.py dist/dropbear-win-x64.exe --service
python tests/windows_usability.py dist/dropbear-win-x86.exe --service
```

本轮本地记录：`build/usability-x64.log`、`build/usability-x86.log`、
`build/usability-regression-0.log`（原生命令/传输）、`build/usability-regression-1.log`
（生命周期）、`build/stress-usability-x64.json`、`build/stress-usability-x86.json`。
`build/` 为 Git 忽略的生成目录；重跑同名命令会覆盖记录。

本轮验证范围是当前 Windows 测试机上的 x64/x86 程序。XP/Server 2003 继续通过
PE/API 静态门禁，尚没有实机证据；本机回归不替代目标机器的网络、权限和部署版本核对。
