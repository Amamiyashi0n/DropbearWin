# 短命令响应优化（2026-09-11）

Windows 命令进程退出后，原先主要依靠会话循环最长 1 秒的超时重新检查退出状态。
现在每个命令注册一次进程等待回调，进程结束时向已有的非阻塞 signal pipe 写入
通知，立即唤醒会话循环。回调不操作 SSH 通道或 Job；会话线程继续负责回收和
发送退出码。注销等待时等回调结束，再关闭进程句柄并复用登记槽，避免回调访问
已复用记录。原有一秒超时保留为异常/退出路径兜底。

输出处理未提前截断：仍然等待管道真实 EOF。使用 Windows XP 支持的旧式线程池
等待 API，没有新增运行库依赖。

## 实测

使用 `tests/windows_latency.py`，在同一本机回环、持久 SSH 连接上测量从发送命令
到读完 stdout/stderr 并收到退出码的总耗时。每类预热 5 次，再统计 30 次。
前后测试在其他回归负载启动之前完成。只采集了 x64 旧版基线。

| 命令 | x64 旧版中位数 | x64 新版中位数 | x64 旧版 P95 | x64 新版 P95 | x86 新版中位数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `echo latency` | 1098.0 ms | 78.2 ms | 1138.6 ms | 102.8 ms | 75.3 ms |
| `exit /b 7`（无输出） | 1109.8 ms | 68.5 ms | 1418.7 ms | 86.2 ms | 70.3 ms |

x64 两类命令中位延迟分别下降约 92.9% 和 93.8%。这是本机短命令结果，不包含
建立 SSH 连接的成本，也不代表网络环境或长任务的加速比例。

## 验证

- x64/x86 构建和 PE/API 兼容门禁通过。
- 两个架构的 CMD/PowerShell 欢迎页、参数、二进制 stdin、大块输出、stderr、
  退出码和 SFTP 回归通过。
- 两个架构的断线、channel 关闭、监听进程崩溃、进程树回收和真实 SCM 启停测试通过。
- 两个架构重新跑 4/12/24 连接压力测试，包含每架构 500 条命令、80 次欢迎页、
  24 路文件往返传输、100 次登录断连与认证前限流。

回归发现测试脚本在强制停止监听进程后立即删除临时日志，有时早于连接进程释放
继承句柄；脚本现在对该删除操作限时重试，超过 10 秒仍报告失败。

原始延迟记录在 `build/latency-before.json`、`build/latency-after-x64.json` 和
`build/latency-after-x86.json`；压力记录在 `build/stress-optimized-x64.json` 和
`build/stress-optimized-x86.json`，包含对应二进制 SHA-256。这些是本地生成文件。
